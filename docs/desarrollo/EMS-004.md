# EMS-004 — Solicitudes y reservas reales

Estado: **COMPLETADO**
Fecha: 2026-10-13

## Resultado

Una cuenta verificada puede solicitar una publicación ajena, consultar y cancelar su solicitud pendiente. El publicador ve interesados mediante DTO mínimos sin correo, teléfono ni dirección, y puede aceptar o rechazar. Aceptar crea una única reserva `PENDING_PAYMENT`, marca la publicación `RESERVED` y fija 24 horas exactas con hora PostgreSQL. La UI separa «Artículo: Gratis» de «Servicio de conexión: $1.000 CLP» y mantiene pago deshabilitado.

No se implementaron proveedor de pagos, checkout, webhook, estado `PAID`, desbloqueo de contacto, chat ni entrega.

## Arquitectura

```text
App Router / rutas HTTP / UI responsive
        │ sesión y autorización en servidor
        ▼
reservation application ports + DTO mínimos
        │
        ├── domain: estados y regla temporal pura
        ├── infrastructure: transacciones PostgreSQL
        └── worker: reservation_expire_due + npm run reservations:expire
```

El dominio no importa Next.js, `pg` ni APIs externas. El repositorio deriva actor y propiedad desde la sesión/DB, bloquea filas de solicitud/publicación, valida el estado bajo el mismo lock y deja a PostgreSQL como autoridad horaria.

## Estados y concurrencia

- Solicitud: `PENDING → ACCEPTED | REJECTED | CANCELLED`.
- Reserva: `PENDING_PAYMENT → EXPIRED | CANCELLED`.
- Publicación técnica: `PUBLISHED → RESERVED → PUBLISHED` por aceptación y liberación.
- No existe `PAID` ni transición tardía de vuelta a `PENDING_PAYMENT`.
- EMS-004.3 reemplazó el rechazo automático: una aceptación conserva las demás solicitudes `PENDING` en espera mientras la publicación está `RESERVED`.
- La restricción parcial de reserva activa y el lock de publicación impiden dos ganadores.
- Cancelación/expiración libera solo si la publicación todavía está `RESERVED`.

## Endpoints

| Endpoint | Operación | Regla principal |
|---|---|---|
| `POST /api/requests` | solicitar por `listingSlug` | autenticado, verificado, publicación ajena y `PUBLISHED` |
| `GET /api/requests?scope=sent|received` | listar solicitudes | solo actor o propietario, DTO mínimo |
| `PATCH /api/requests/{id}` | `cancel`, `reject`, `accept` | autorización y estado bajo lock |
| `GET /api/reservations?scope=mine|owned` | listar reservas | solo participante correspondiente |
| `GET /api/reservations/{id}` | ver reserva e historial | receptor o publicador; terceros reciben 404 |
| `PATCH /api/reservations/{id}` | cancelar antes del pago | participante y `PENDING_PAYMENT` vigente |

## Matriz de autorización

| Recurso/acción | Anónimo | Solicitante | Publicador | Tercero |
|---|---:|---:|---:|---:|
| Crear solicitud | no | sí, correo verificado | no sobre artículo propio | sí sobre artículo ajeno |
| Cancelar solicitud pendiente | no | sí, propia | no | no |
| Aceptar/rechazar | no | no | sí, publicación propia | no |
| Ver reserva | no | sí, propia | sí, propia | no |
| Simular pago/`PAID` | no | no | no | no |
| Ver contacto privado | no | no | no | no |

Las respuestas no incluyen correo, teléfono, dirección, identificadores de participantes ni claves físicas. Desde EMS-004.3 el publicador recibe únicamente el nombre público o alias necesario para distinguir interesados.

## Worker y operación

`npm run reservations:expire` llama una vez a la función transaccional por lotes. El servicio Compose `reservation-worker` usa `--watch` y repite cada 60 segundos en un proceso separado del frontend. Puede haber reintentos o instancias concurrentes sin duplicar expiraciones gracias a los locks y estados terminales. En producción todavía deberán definirse monitorización y alertas. Las lecturas privadas y operaciones críticas realizan además una comprobación de vencimientos.
