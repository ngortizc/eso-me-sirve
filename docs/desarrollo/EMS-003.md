# EMS-003 — Publicaciones reales y almacenamiento de fotografías

Estado: **COMPLETADO**
Fecha: 2026-10-12

## Resultado

Una cuenta con correo verificado puede guardar un borrador o publicar un artículo gratuito con entre una y ocho fotografías, cerrar sesión y encontrarlo posteriormente en el catálogo. El propietario puede editar contenido, agregar/eliminar fotografías, cambiar la principal, pausar, reactivar o retirar. Las operaciones de administración vuelven a validar sesión y propiedad en el servidor.

No se implementaron solicitudes, reservas, pagos, entrega de contacto ni proveedores comerciales.

## Arquitectura implementada

```text
App Router / UI y rutas HTTP
        │ sesión + DTO + validación de transporte
        ▼
application/create-listing + puertos ListingRepository / PhotoStorage
        │
        ├── domain: estados, transiciones y validaciones puras
        ├── infrastructure/PostgresListingRepository ── PostgreSQL
        └── infrastructure/LocalPhotoStorage ────────── filesystem persistente
```

El dominio no importa Next.js, `pg`, Sharp ni filesystem. El adaptador HTTP obtiene `ownerId` exclusivamente de la sesión; rechaza `ownerId`, `userId`, precios y montos enviados por el navegador. El catálogo y detalle usan DTO públicos sin propietario, correo, teléfono, dirección, clave física ni otros campos internos.

La portada es dinámica porque consulta publicaciones runtime. `/explorar` ofrece texto, categoría, región, comuna y paginación, ordenados por fecha de publicación descendente. Los datos de demostración permanecen en `src/shared/demo` y se usan solo como fallback identificado; no se insertan en las tablas reales.

## Modelo y migración

`db/migrations/1760270400000_listings.sql` crea:

- `listing_category`: catálogo controlado de seis categorías;
- `listing_public_region`: las 16 regiones de Chile;
- `listing_public_commune`: 22 comunas habilitadas para el piloto;
- `listing`: UUID estable, slug público, propietario, contenido, condición, estado, fechas y versión optimista;
- `listing_public_location`: región y comuna públicas, sin calle ni dirección exacta;
- `listing_photo`: clave opaca de almacenamiento, posición, principal, dimensiones, tamaños, formato, hash de fuente y versión de procesamiento;
- `listing_storage_cleanup`: ledger idempotente para reintentar eliminaciones físicas;
- `listing_upload_rate_limit`: ventanas persistidas de carga por usuario.

Incluye claves foráneas, índices de catálogo/filtros, `tsvector` español, unicidad diferible de posiciones, una única principal mediante índice parcial y triggers diferibles de consistencia. PostgreSQL no almacena binarios.

La migración aplicada figura en `pgmigrations` como `1760270400000_listings`. La evidencia local mostró 6 categorías, 16 regiones y 22 comunas.

## Estados

- `DRAFT → PUBLISHED | REMOVED`
- `PUBLISHED → PAUSED | REMOVED`
- `PAUSED → PUBLISHED | REMOVED`
- `REMOVED` es terminal.

Solo `PUBLISHED` es público. Publicar o reactivar requiere todos los campos, ubicación válida, entre una y ocho fotos y exactamente una principal. Las reglas se validan en dominio y nuevamente mediante constraints/triggers de base de datos. Los futuros estados de reserva/entrega continúan pendientes.

## Fotografías

El contrato `PhotoStorage` expone `store`, `read` y `delete` con variantes `catalog` y `detail`. `LocalPhotoStorage` es el único adaptador de EMS-003 y queda documentado en ADR-0014; el proveedor Object Storage sigue pendiente en ADR-013.

Controles implementados:

- máximo ocho fotos por publicación y 10 MB por archivo;
- detección del contenido binario real con Sharp, coherencia con MIME declarado y aceptación solo de JPEG, PNG o WebP;
- máximo 8.000 píxeles por lado y 40 megapíxeles; se rechazan imágenes animadas;
- orientación, decodificación y recodificación WebP sin copiar EXIF/GPS;
- variantes de catálogo (máximo 640 px) y detalle (máximo 1.600 px); no se conserva ni sirve el original;
- claves aleatorias de 32 bytes, validación estricta y resolución siempre bajo la raíz configurada;
- escritura temporal y renombrado atómico;
- compensación si falla la transacción, más ledger para reintentar borrado;
- endpoint de medios que autoriza publicación pública o propietario y nunca revela la ruta/clave física.

En desarrollo npm y Docker comparten `.data/listing-photos`; el directorio está ignorado por Git. El ejemplo productivo conserva un volumen separado solo como referencia.

## Seguridad y moderación

- Sesión válida y correo verificado son obligatorios para crear o administrar.
- Cada mutación comprueba propiedad cerca del acceso SQL; un usuario ajeno obtiene 403.
- Consultas parametrizadas, transición de estado controlada y versión optimista.
- Cinco cargas por usuario cada diez minutos; límite de `Content-Length` cuando está disponible y límites por archivo durante el procesamiento.
- Validación textual bloquea formatos comunes de teléfono, correo, dirección exacta, precio, venta y permuta.
- EXIF/GPS se elimina; logs registran resultado/estado sin contenido, identidad ni claves.

Pendiente antes de producción: límite de cuerpo en proxy antes del parseo multipart, antivirus, detección/OCR de datos personales dentro de fotografías, moderación humana y apelación, worker recurrente del ledger de limpieza, reconciliación de huérfanos, catálogo nacional completo de comunas y proveedor Object Storage con cifrado, lifecycle, backups y control de acceso. Los filtros de texto son preventivos y pueden tener falsos positivos o ser evadidos; no reemplazan moderación.

Abrir `/registro`, verificar con el buzón local, ingresar y visitar `/publicar`. `PHOTO_STORAGE_ROOT` debe apuntar a un directorio persistente escribible; no debe estar bajo `public/`.

## Riesgos y próximo trabajo

- El filesystem local no escala horizontalmente y no es una decisión productiva; seleccionar Object Storage sigue pendiente.
- No existe aún un worker automático para reintentar filas de `listing_storage_cleanup`.
- La carga multipart necesita un límite temprano en reverse proxy para resistir cuerpos sin `Content-Length`.
- La aplicación conserva datos E2E en la base local; son datos de prueba claramente identificables y no deben migrarse a otro entorno.
- El audit completo conserva cinco alertas altas de herramientas de desarrollo ya asociadas a la cadena ESLint; producción reporta cero.

Siguiente trabajo recomendado: EMS-004 para completar exploración/ubicación (catálogo nacional, URL canónica de filtros, rendimiento y accesibilidad), sin anticipar solicitudes, reservas ni pagos de EMS-005/006.
