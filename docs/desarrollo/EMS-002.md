# EMS-002 — Identidad, autenticación y autorización

Estado: **COMPLETADO**  
Fecha: 2026-10-12

## Diagnóstico de hidratación

El aviso original de `/publicar` mostraba `data-kantu` y `data-xt-extension-active`. La investigación produjo tres evidencias:

1. `rg` no encuentra esos atributos ni `suppressHydrationWarning` en el repositorio.
2. El HTML crudo servido para `/publicar` no contiene ninguno de los atributos.
3. Chromium limpio de Playwright carga e hidrata la página sin mensajes y sin esos atributos en el DOM.

Conclusión: una extensión del navegador modificó el DOM antes de que React hidratara. Los prefijos corresponden a estado inyectado por extensiones, no a output del servidor ni del cliente de Eso Me Sirve. No se añadió `suppressHydrationWarning`. Una prueba E2E conserva este diagnóstico. Las capturas usan `caret: "initial"`, porque Playwright puede ocultar temporalmente el cursor agregando un `style` antes de terminar la hidratación y producir otro falso positivo distinto.

## Decisión técnica

Se seleccionó Better Auth 1.7.7 después de evaluar una implementación propia, Auth.js y servicios alojados. La justificación completa está en `ADR-0010`.

- integración oficial con Next.js App Router;
- PostgreSQL directo mediante `pg.Pool`;
- email/contraseña, verificación, recuperación y sesiones de base de datos;
- `scrypt` mantenido y nativo de Node para hashes;
- rate limiting persistido;
- sin ORM nuevo ni proveedor externo de identidad.

La CLI `auth` 1.7.7 generó el esquema inicial. El SQL se revisó y se versionó mediante el mecanismo existente de `node-pg-migrate`; la CLI no aplica cambios fuera de las migraciones del proyecto.

## Arquitectura implementada

```text
src/app
├─ ingresar, registro, verificación, recuperación, perfil y admin
├─ api/auth/[...all]                 adaptador HTTP Better Auth + sanitización
├─ api/identity/verify-email         canje seguro por POST
├─ api/sessions                      DTO y revocación sin tokens
└─ api/users/[userId]/profile        autorización de propietario/ADMIN

src/modules/identity
├─ domain                            correo y roles puros
├─ application                       sesión, retorno seguro, autorización, puertos
└─ infrastructure                    Better Auth, correo local, PostgreSQL

src/modules/profiles/infrastructure  repositorio y DTO mínimo
```

Las páginas `/publicar`, `/mis-cosas`, `/perfil` y `/admin` comprueban la sesión o rol en servidor. Solicitar un artículo comprueba sesión y redirige a `/ingresar` con un `returnTo` interno validado; la acción continúa siendo demostrativa porque EMS-002 no persiste reservas. El endpoint de perfil repite autorización junto al acceso de datos y usa consultas parametrizadas.

## Modelo de datos y migraciones

`1760263200000_identity.sql` crea:

- `identity_user`: nombre, correo normalizado único, verificación, rol `USER|ADMIN` y comuna opcional;
- `identity_account`: proveedor `credential` y hash de contraseña;
- `identity_session`: sesiones revocables con expiración, agente e IP;
- `identity_verification`: valores efímeros de recuperación/verificación;
- `identity_rate_limit`: contadores atómicos persistidos;
- `identity_test_email`: buzón exclusivo de desarrollo.

`1760266800000_identity_token_consumption.sql` agrega digests SHA-256 de verificaciones consumidas para garantizar un único uso sin almacenar el token original. Todas las fechas usan `timestamptz`; la interfaz formatea sesiones en `America/Santiago`.

## Controles de seguridad

- Contraseña mínima de 12 y máxima de 128 caracteres; hash `scrypt`; nunca se devuelve el hash.
- Cookie opaca HttpOnly, SameSite=Lax y Secure cuando `NODE_ENV=production`.
- Correo normalizado a minúsculas por Better Auth y por la interfaz; constraint en DB evita valores no normalizados.
- Verificación obligatoria antes de login; enlaces de verificación y recuperación con 15 minutos de vigencia.
- Verificación y recuperación de un solo uso; reset revoca todas las sesiones anteriores.
- Rate limits: login 5/minuto, recuperación/verificación 3/minuto y límites generales persistidos.
- Registro y recuperación responden sin confirmar si el correo existe; la UI usa mensajes genéricos.
- `returnTo` rechaza orígenes externos, rutas `//` y barras invertidas.
- Respuestas HTTP de autenticación eliminan recursivamente token, password, hash y tokens de proveedores; sesiones visibles usan un DTO sin token ni IP.
- Los tokens de correo viajan en el fragmento `#` y se canjean por POST, por lo que no aparecen en URL HTTP, HTML del servidor ni logs de acceso.
- Roles son propiedad del servidor: el input de registro no puede asignar `ADMIN`.
- No existen campos de teléfono o dirección en este modelo ni se añadieron endpoints de contacto.

## Correo local

`IdentityEmailDelivery` es un puerto. EMS-002 implementa solamente `DatabaseEmailDelivery`, habilitado cuando:

```dotenv
APP_ENV=development
EMAIL_DELIVERY_MODE=database
```

Los enlaces se consultan de forma explícita con:

```powershell
npm run mailbox:latest -- correo@ejemplo.cl EMAIL_VERIFICATION
npm run mailbox:latest -- correo@ejemplo.cl PASSWORD_RESET
```

No hay endpoint web de buzón ni envío real. En producción `disableSignUp` permanece activo hasta incorporar un adaptador de correo aprobado.

## Variables de entorno

| Variable | Uso |
|---|---|
| `DATABASE_URL` | conexión privada a PostgreSQL |
| `BETTER_AUTH_SECRET` | secreto de alta entropía, mínimo 32 caracteres |
| `BETTER_AUTH_URL` | origen canónico HTTPS en producción |
| `APP_ENV` | `development` habilita mecanismos locales; `production` los bloquea |
| `EMAIL_DELIVERY_MODE` | únicamente `database` para desarrollo en EMS-002 |

`.env.example` contiene solo valores locales conocidos. `.env` permanece ignorado por Git. El ejemplo productivo exige inyección externa del secreto.

La etapa de compilación de la imagen define `BETTER_AUTH_VALIDATE_SCHEMA=false`: no dispone de red hacia PostgreSQL y no ejecuta la aplicación. En runtime la variable no existe, la validación vuelve a estar activa y readiness comprueba además la conexión real.

## Cómo probar

```powershell
docker compose up -d db
npm run db:migrate
npm run dev
```

Abrir `/registro`, consultar el buzón local, abrir el enlace una vez y luego usar `/ingresar`. `/perfil` permite cambiar nombre/comuna, revisar sesiones, cerrar otra sesión o cerrar la actual. `/recuperar` genera un enlace local equivalente para cambiar contraseña.

## Riesgos y pendientes

- Proveedor de correo, reputación de dominio, colas/outbox, reintentos y observabilidad siguen pendientes.
- Antes de producción debe definirse el proxy confiable para obtener la IP real sin aceptar encabezados falsificables. El encabezado de aislamiento E2E existe solo en `APP_ENV=development`.
- Falta política aprobada de retención y eliminación de cuentas/sesiones/correos locales; el buzón y digests requerirán limpieza programada.
- No se implementó MFA, cambio de correo, eliminación de cuenta ni recuperación administrativa.
- El `npm audit` completo conserva la alerta de desarrollo de `braces`/ESLint ya documentada en ADR-0008; producción reporta cero.
- ORM continúa pendiente en ADR-009; Better Auth usa Kysely internamente como detalle del adaptador y no lo convierte en ORM de la aplicación.
- Playwright/Next advierte que una imagen demostrativa puede convertirse en LCP en el catálogo móvil; conviene priorizarla al abordar rendimiento en EMS-003.
